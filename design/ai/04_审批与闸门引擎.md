# 04 · 审批与闸门引擎

> 这是全系统最核心的代码，也是红线的落点。实现优先级最高、测试最严。
> 目标：**让“未批不执行 / 默认无批准权 / 判定由规则”成为代码结构，而不是约定。**

## 1. 结构总览

```
 Agent / 人的请求
        │
        ▼
  ┌──────────── Tool Gate（唯一出口 call_tool）────────────┐
  │ 1 身份戳记 2 注册表查找(未登记=DENY) 3 authorize(actor)  │
  │ 4 Gatekeeper 判定 5 安全带(原子预留) 6 若需人批：按      │
  │ approval_id 绑定校验+CAS 消费  7 执行  8 审计(独立事务) │
  └──────────────────────────────────────────────────────────┘
        │                              ▲
        ▼                              │ 生成/更新
   外部世界（文件、LLM、平台适配器）     审批单 approvals ◀── 人（唯一批准者）
```

- **Gatekeeper** = 纯函数式判定模块：输入 `(action, facts, ruleset)`，输出 `Decision`。**不依赖 LLM、网络**（INV-8）。
- **Tool Gate** = 所有副作用的唯一入口。业务代码不得绕过（CI 静态检查：除 `toolgate/` 之外不得 import HTTP 客户端、LLM SDK、适配器）。
- **Approvals** = 审批单状态机 + 证据生成器 + 前置条件检查。

## 2. 动作注册表（Action Registry）

动作注册表是**代码里的一张常量表**，每个 `ACT-*` 必须登记才能被调用。字段：

| 字段 | 含义 |
|---|---|
| `name` | `ACT-*` |
| `disposition` | `AUTO`（Agent 可直接做）/ `HUMAN_APPROVAL`（要审批单）/ `HUMAN_INITIATED`（只有人能发起，点击即决定，不生成审批单）/ `NEVER`（不得存在） |
| `reversibility` | `REVERSIBLE` / `COMPENSABLE` / `IRREVERSIBLE` |
| `undo` | 撤回/补偿方式；`IRREVERSIBLE` 必须显式写 `none` |
| `external_effect` | 是否影响本系统之外（平台、外部服务、对外展示） |
| `grantable` | 是否可进授权清单 |
| `approver_role` | 需要的批准角色（见 §10） |
| `evidence_kinds[]` | 审批单必须生成的证据类型（§4） |
| `preconditions[]` | 前置条件检查器名（§5） |
| `guardrails[]` | 绑定的安全带（§8） |

## 3. Gatekeeper

### 3.1 输出

```python
class Decision(Enum):
    ALLOW_AUTO        # 允许自动执行（留痕、受安全带约束）
    REQUIRE_HUMAN     # 需要人批（生成/匹配审批单）
    BLOCK             # 命中阻断规则；不进审批；只能改后重来
    HOLD              # 不确定/缺事实/判定器故障；等人补，不执行

@dataclass(frozen=True)
class Verdict:
    decision: Decision
    reasons: list[Reason]        # 每条含 rule_id、rule_version、事实快照引用
    missing_facts: list[str]     # HOLD 时：缺什么
    ruleset_version: str
```

### 3.2 判定顺序（与 01 §6 一致）

```python
def judge(actor, action_name, facts, ruleset) -> Verdict:
    # Tool Gate 先 authorize(actor, spec)：Agent 只能调用 disposition=AUTO 且在其白名单内的动作；
    # HUMAN_INITIATED 只允许 users.kind='human' 且角色匹配；否则 403 + 审计（AC-39）。
    try:
        spec = REGISTRY.get(action_name)
        if spec is None:                                   return DENY("ACTION_FORBIDDEN")      # INV-7：未登记=拒绝并审计，不生成审批单
        if ruleset is None or ruleset.expired(now):        return HOLD("ruleset_unavailable")      # INV-9
        results = ruleset.evaluate(spec, facts)            # 三值：MATCH / NO_MATCH / UNKNOWN（每条规则声明 requires_facts）
        blocks = [r for r in results if r.value == "MATCH" and r.severity == "BLOCK"]
        if blocks:                                         return BLOCK(blocks)
        missing = (required_facts(spec) | {f for r in results if r.value == "UNKNOWN" for f in r.requires_facts}) - facts.known()
        if missing:                                        return HOLD(missing)                    # 缺 ⇒ UNKNOWN ⇒ 停
        if spec.disposition == "AUTO":                     return ALLOW_AUTO
        return REQUIRE_HUMAN
    except Exception as e:                                 # 判定器自己出错 ⇒ 不确定 ⇒ HOLD
        return HOLD("judge_error", detail=repr(e))
```

要点：

- **永远不返回 ALLOW 作为异常的结果**（INV-9）；单元测试用故障注入覆盖：规则库读失败、规则过期、事实缺失、除零等。
- 规则评估为**三值**：任一规则 UNKNOWN（缺它依赖的事实）→ HOLD，不得当作“未命中”；属性测试：删掉任一事实，结果不得是 ALLOW（AC-40）。
- `required_facts(spec)`：由注册表声明，例如 ACT-APPROVE-ASSETS 需要 `cost_snapshot`、`fx_rate`、`compliance_report`、`license_evidence`…。
- 规则库有**发布版本**与**有效期**；版本被替换时，所有依赖旧版本的待批单重新跑前置条件（§5）。
- `UNVERIFIED` 规则可以产生 BLOCK/WARN，**不能**用来产生放行结论（03 §5.3）。

### 3.3 规则库的三态新鲜度

`ruleset.freshness ∈ {FRESH, STALE, NOT_INTEGRATED}`：

- `FRESH`：正常；
- `STALE`（超过配置的复核周期）：依赖规则库的动作一律 `HOLD`，审批单写“规则库已过期 N 小时，批准等于按可能已失效的规则执行”，且需 Owner 先 `ACT-RULESET-RENEW`（一次性、留痕、即时生效）才可继续；伪代码中 `ruleset.expired` 即代表 STALE；`NOT_INTEGRATED` 在 `evaluate` 内按保守默认处理；
- `NOT_INTEGRATED`（某规则族本期没有外部数据源，如 U-5）：该规则族取保守默认（白名单为空=不可选），**不是拒绝服务**，也不写成“新鲜”。

## 4. 审批单（Approval）

### 4.1 字段

| 字段 | 说明 |
|---|---|
| `id` / `shop_id` / `action_type` | |
| `title` | 动词开头 + 对象 + 关键数值（系统模板生成） |
| `subject_refs[]` | 被批对象（候选/素材集/上架单） |
| `what_changes` | 将要发生的变化（diff，对象级） |
| `why` | ≤30 字结论（模板 + 事实） |
| `impact` | 对象数、金额敞口（JPY）、是否对外可见、是否不可逆 |

| `version` / 内容不可变 | 进入 PENDING 后，审批单内容不可变（触发器只放行 `status/decision/decided_*` 列）；前置条件当前值与查看记录放进 `approval_views`/`approval_checks` 表；内容要变就开新单并 `SUPERSEDED` 旧单 |

| `status` / `pending_since` | 状态机（§5.3） |
| `created_by_agent_id` | 提单的 Agent；**批准人不可是它** |
| `approver_user_id` / `decided_at` / `decision_note` | 批准人（自然人） |
| `delegated_via_grant_id` | 若由授权清单代批，指向授权；**`approver_user_id` 与 `delegated_via_grant_id` 恰好一个非空**（`CHECK`），审计显示“由授权 G-xx（授权人 …）代批”，不显示为本人批准 |

## 5. 前置条件、哈希与作废（RL-1 的实现）

### 5.1 钉住“批的是什么”

批准时固化两样东西：

1. **载荷哈希** `payload_hash = sha256(JCS(payload))`：**只含“要写到平台上的字段”**（03 §6.1），素材以文件内容哈希入载荷；**不含** `cost_snapshot_id/fx_rate_id/ruleset_version/direction_version` 等事实引用（它们放 `fact_snapshot`，由带容差的 PC-* 判断，否则每天换一次汇率编号就会让所有在途单集体作废）。规范化：RFC 8785 JCS；金额为 JPY 整数字符串；Unicode NFC；所有 CNY×汇率在**逐项**四舍五入到 JPY 整数后再求和，margin 以 `numeric` 比较到小数 4 位（属性测试保证 Python 与 PG 结果一致，AC-41）。
2. **事实快照** `fact_snapshot`：`cost_snapshot`（分项成本）、`fx_rate_id`、`ruleset_version`、`direction_version`、`shop_profile_version`、`source_item_versions`。

> 哈希只证明**没被改写**，不证明**事实还成立**。所以还需要前置条件。

### 5.2 前置条件（执行前与审批期间持续检查）

| 前置条件 | 失效判据 |
|---|---|
| PC-PAYLOAD | 当前载荷哈希 ≠ 批准哈希 |
| PC-FX-FRESH | 汇率取数距今 > `fx_max_age_hours`（缺省 24）→ HOLD（请人更新汇率；属事实过期，不是审批过期） |
| PC-SOURCE-FRESH | 货源价/有货确认距今 > `source_max_age_days`（缺省 7）→ HOLD（请人重新确认） |
| PC-TAX | `tax_regime` 过期、变更或进入新的有效期 |
| PC-FX | `|当前汇率 − 快照汇率| / 快照汇率 > 3%`（可配，只能收紧） |
| PC-COST | 重算毛利 < 毛利底线，或任一成本项状态变为 MISSING |
| PC-PRICE-FLOOR | 价格 ≤ 成本地板价 |
| PC-SOURCE | 货源价变动 > 5% 或货源条目被修改/下线 |
| PC-RULES | 规则库发布了新版本且对该对象重跑出新的 BLOCK |
| PC-G0 | 类目白名单变动使该品不再 ALLOW |
| PC-SHOP | 店铺档案中已确认项（特商法、运费模板、発送日数）发生变化 |
| PC-DIRECTION | 方向卡版本变化且该品不再满足新方向 |
| PC-ASSET | 素材文件内容哈希变化 |

**对象绑定（P0-3）**：执行请求必须带 `approval_id`，Tool Gate 逐项校验：动作映射一致、`subject_refs` 与执行目标逐个相等且只能是 **id 列表**（不得是查询条件）、`payload_hash == hash(build_payload(subject))`、`shop_id` 一致；并以 CAS 单次消费：`UPDATE approvals SET status='EXECUTING' WHERE id=$1 AND status='APPROVED' RETURNING …`，同一张批准不能被用两次或用于别的对象。`decide` 请求必须带 `If-Match: version` 与 `payload_hash`，不符 → 412，内容一变就是新单；对未结单建部分唯一索引 `UNIQUE(shop_id, action_type, subject_key) WHERE status IN ('DRAFT','PENDING','APPROVED','EXECUTING')`。

**通道 A 的执行窗口（P0-6）**：真正不可逆的一步是人在后台操作，可能晚于清单发放数天。因此 ① `listing_jobs=PENDING` 与 `APPROVED(未执行)` 一样纳入事实变更与每日新鲜度重算；一旦失效，清单标“作废，不要执行”、复制与素材包下载同时失效，并回到流水线重新 judge；② **回填时再跑一遍全部 PC**：若人已在后台提交而前置已失效 → 新状态 `EXECUTED_STALE`（HELD，只能“去后台下架”或“走新单补批”）；③ 通道 A 下 `EXECUTING`=清单已发放，`EXECUTED`=回填 MATCH；批准前清单与素材包不可下载。

触发时机：①规则库/汇率/方向卡等**事实变更事件**发生时，以及**每日定时的新鲜度扫描**（汇率与货源确认日期可能没有人去改，所以不能只靠变更事件），对所有 `PENDING` 与 `APPROVED(未执行)` 的单重算；②**执行前最后一刻**在 Tool Gate 内再检一遍。

### 5.3 审批单状态机（注意：没有任何“按时间触发”的边）

```
DRAFT ─▶ PENDING ─┬▶ APPROVED ─▶ EXECUTING ─▶ EXECUTED
                  │                │
                  │                └▶ EXEC_FAILED ─(人点重试，重新校验前置)─▶ EXECUTING
                  ├▶ REJECTED   （人拒绝，终态；**拒绝抑制**：同一对象在事实变化或人主动恢复前，Pilot 不再重新提案）
                  ├▶ RETURNED   （退回改写，终态；产出新版本素材 → 新单）
                  ├▶ SUPERSEDED （被同对象的新单取代）
                  └▶ VOID       （前置失效；终态；自动生成后继单 PENDING，带 diff）
APPROVED ─▶ VOID （执行前发现前置失效）；EXECUTING ─▶ VOID；EXEC_FAILED ─▶ VOID
EXECUTING ─▶ OUTCOME_UNKNOWN（外部调用超时/结果不明：**先读回再决定是否重试，不得假设成功或失败**，防止通道 B 重复上架）
worker 崩溃后卡在 EXECUTING 的任务由租约超时回收并走 OUTCOME_UNKNOWN。DRAFT 仅可 → PENDING 或被丢弃。
```

INV-2 的测试：用状态机转换表断言**不存在**由时钟触发到 `APPROVED/REJECTED/VOID` 的边；用假时钟快进 1 年，所有 `PENDING` 仍为 `PENDING`。

### 5.4 VOID 与后继单

`VOID` 时：写 `void_reasons[]`（哪个前置、旧值→新值）→ **把对象送回流水线对应阶段重新 judge**（PC-COST/PC-PRICE-FLOOR 失效的品直接回候选；PC-ASSET 失效必须重走 Creator 与合规复检），**只有结果仍是 REQUIRE_HUMAN 时才生成后继单**；同一对象的多个变化合并成一张；同一对象 24 小时内 VOID ≥3 次 → HOLD“事实不稳定”；改一次费率卡波及的多张单合并为一条通知。后继单，`what_changes` 写成“与上一次批准相比：成本 ¥1,240→¥1,390，汇率 …”→ 通知。系统**不会**“按批准的精神”调参数继续执行。

### 5.5 挂起、终止与重跑的三条不变量

> 这三条针对「停住的东西」，与审批单的挂起（§5.3）不是一回事：审批单等的是人的决定，批次等的是缺的输入。

1. **挂起不自动重试**。缺的是事实或人的输入，自动重试只会把同一个错误重复 N 次。重试只适用于确定性失败（网络、平台报错），且受 `retry_limit` 约束。
2. **终止批次不回滚已完成的部分**。本期没有「撤销已执行」的能力；终止只是「不再继续」，已经写进后台的东西仍在。终止时必须生成去后台处理清单（对象 + 字段路径 + 复核人）并进审计。
3. **补输入后要重跑预检，不只补那一条**。补完事实，前置条件可能已经变了；重跑预检 = 全部前置条件再过一遍，不通过就继续 HOLD。

界面口径（08 §2.4 / SCR-06）：挂起行必须写「需要你做什么」，不出现倒计时；终止按钮旁必须写「已执行部分不会回滚」。

## 6. 执行（Outbox + 幂等）

- 审批 `APPROVED` 与 `execution_jobs` 写入在**同一事务**；worker 取任务，执行前在 Tool Gate 内复检前置（§5.2）。
- 幂等键 = `approval_id + step`；重复投递不产生重复副作用（通道 A 的“清单已生成”与“已回填”也各自幂等）。
- 失败 → `EXEC_FAILED`，原因入审计；**不自动重试对外不可逆动作**，必须人点重试（并重新校验）。

## 7. 授权清单（RL-2 的实现）

### 7.1 结构（`grants`）

```
grant { id, shop_id, action_type (仅可授权动作), envelope(范围包络), created_by(自然人), created_from_approval_id,
        created_at, expires_at (≤ created_at+30d), max_uses, used_count, status ACTIVE|REVOKED|EXPIRED|SUSPENDED,
        revoked_by, revoked_at, sampling_rate }
```

`ACT-SELECT` 的包络：

```json
{ "categories": ["…"], "price_band_jpy": [min, max], "min_margin": 0.25, "max_per_day": 3,
  "require": { "profit_computable": true, "g0_pass": true, "no_degrading": true, "source_grade_min": "B" } }
```

### 7.2 规则

1. **默认无**：没有 ACTIVE 授权就没有代批。
2. **匹配与原子消费**：代批由**确定性代码路径**（grant engine）完成，**不是 LLM Agent 调用 `approval.decide`**——Pilot 的工具白名单里没有它。包络内由系统直接置 APPROVED，并在同一事务内 `UPDATE grants SET used_count=used_count+1 WHERE id=$1 AND status='ACTIVE' AND effective_from<=now() AND expires_at>now() AND used_count<max_uses RETURNING …`（并 `CHECK(used_count<=max_uses)`）；日用量对 grant 行 `FOR UPDATE` 后计数，日界按 Asia/Tokyo。包络拆成列（`categories text[]`、`price_min/max`、`min_margin`、`max_per_day`、`source_grade_min`），收窄触发器逐列比较（`NEW.categories <@ OLD.categories` 等）。任一不满足 → 回到人工审批。
3. **收窄即时**：`PATCH` 只接受“新包络 ⊆ 旧包络”、数值只减不增、`expires_at` 只提前；DB 触发器兜底（INV-6）。
4. **放宽 = 新建**：`ACT-CREATE-GRANT`（HUMAN_INITIATED，Owner 角色），写书面理由，**24 小时后生效**（`effective_from`）。
5. **撤销**：一键，立即生效，无需理由与复核；撤销后同类立刻回落人工。
6. **自动失效**：到期；抽检发现 1 起“被代批但应拒绝”→ 立即 `SUSPENDED` 并回落人批；Owner 复核后才可恢复（不自动恢复；恢复到被暂停前的包络，视为“恢复基线”，即时生效但留痕）。
7. **抽检**：被代批的单按 `sampling_rate`（缺省 20%）进入每周抽检卡，Owner 判 OK/有问题。
8. **永不可授权**：INV-5。界面上这些动作在授权清单页显示为“**不可加入**”（不隐藏，避免让人以为也许能开）。

## 8. 安全带（PR-5 的逐项落地）

> 数值为**初始建议值**；全部在设置里可配，**收紧即时生效，放宽须经 ACT-LOOSEN-RULE（24 小时后生效）**。

| 安全带 | 本期落地 | 初始值 |
|---|---|---|
| 每日上限 | 每日候选数、同意 1 勾选数、生成调用数、模型花费、上架清单数 | 候选 30 / 勾选 10 / 花费 = Owner 设定（未设 = 0 = 不生成）/ 清单 10 |
| 幅度闸门 | 汇率偏离、货源价偏离、售价低于地板价、毛利低于底线 | 3% / 5% / BLOCK / BLOCK |
| 抽样复核 | 自动通过的合规结果周抽检；代批的同意 1 周抽检 | 10% / 20%，每周一张抽检卡（≤10 条） |
| 一键降级 | 每项能力有开关：`ACTIVE` / `SUGGEST_ONLY` / `OFF`；任何人任何时候可往严切，立即生效；往松切走 ACT-LOOSEN-RULE | — |
| 连续失败熔断 | 同类自动动作连续失败 ≥3 次 → 能力自动收紧一档并告警 | 3 |
| 速率熔断 | 单位时间动作数异常暴增 → 暂停自动流水线转人看 | 缺省 60 次/分钟 |
| 回滚路径 | 每个 ACT 登记 `undo`；测试断言非空或显式 `none`。上架的补偿 = 下架（人在后台）；24 小时内的“一键下架”在通道 B 提供 | — |
| 参数核对 | 批准哈希 + 前置条件（§5），执行时再校验 | — |

**恢复基线 vs 放宽基线（P1-5）**：熔断/降级后**恢复到人曾批准过的基线**（一键、即时、留痕）；**放宽到比已批准基线更松**才走 24 小时延迟（`pending_changes` 表统一承载）。`agents.status`、`capability_flags`、`guardrail_settings` 合并为一套开关与一张 `pending_changes` 表。判据统一：“这次变更会让更多对象通过”即为放宽——新增品类白名单 ALLOW、修改 `allow_with_flag`、删除词库条目、方向卡降毛利底线/加类目、预算上调都属放宽（方向卡由此**也走 24 小时延迟**，覆盖 02/03 里“保存即生效”的旧说法）。

**止损方向不等审批，扩张方向必须人批**：往回收（暂停某能力、收紧阈值、放弃某品）立即生效、事后通知；往外放（放宽规则、加预算、恢复能力、加授权）必须人批（并 24 小时延迟）。这样不会出现“暂停→恢复→暂停”的抖动。

## 9. 防盖章与人时账本（PR-1 的度量）

- **required_viewed**：审批单声明必须查看的证据分区；前端记录展开/查看事件，服务端在批准请求里校验 `viewed ⊇ required_viewed`，否则 `409 EVIDENCE_NOT_VIEWED`。这是“真看过”的最低门槛，不是时间延迟。
- **批量上限**：同意 1 单批勾选数 ≤ `selection_cap`；DEGRADING 行必须逐行展开；高风险行永不折叠。
- **退回原因**：预定义原因必选 + 自由文本选填。
- **人时账本 `human_effort_log`**：每次人的决定记 `action_type`、`decision_seconds`（卡片打开到点击，上限 600）、是否批量、是否积压后批准。派生指标：**今日待办数与预计用时**、**日均出手次数**、**积压批准占比**（挂起 >4 小时才批的比例；高 = 被淹没或在盖章）。首页展示，管理视角可看周趋势。
- 排序：待批队列由服务端按“风险、挂起时长、金额敞口、不可逆性、阻塞下游数”算优先级，界面不能改成纯按时间。

## 10. 角色、单人运行与独立性补偿

| 角色 | 能做什么 |
|---|---|
| Owner（老板） | 给方向、定规则、批 Owner 类动作（超预算放行、规则放宽、授权新建、风险确认）。**不批日常两道同意**（但 Owner 与 Operator 可由同一自然人担任） |
| Operator（运营/店长） | 唯一必备审批人：同意 1、同意 2；通道 A 的清单执行 |

**单人运行**（P1 的现实：同一自然人兼 Owner 与 Operator）：

- **允许**，但界面在页眉常驻标注“单人运行”（不是装作合规）；
- **Agent 不能签**（没有“机器签”；ADR-13）。“自批自提”的冲突在本系统里不存在：“发起”的是 Agent（生成选品、素材、清单）；人只做决定，因此**不存在自批自己提的单**这一冲突；
- 用以下措施补偿独立性不足：① 放宽类动作 24 小时延迟 + 二次确认；② 每周抽检卡（自动通过的合规结果 + 代批的同意 1 + 全部 WARN 确认）；③ 防盖章 `required_viewed`；④ “自批自执”（通道 A 里同一人批并执行）标记进审计高危视图；⑤ 积压批准占比阈值告警；
- 当 `users` 中出现第二个自然人 Operator/Owner 时，系统自动启用**制作者≠批准者**：人工编辑过素材的人不能批该素材的同意 2（DB `CHECK`+应用校验）。

## 11. 催办与升级（只提醒，不改变状态）

`PENDING` 单：创建即通知 → +1 小时再提醒 → +4 小时升级通知 Owner → 之后每 24 小时提醒；全部是**提醒**，不改变状态、不放行、不放弃。界面时效卡写“长期有效，等待批准 · 已挂起 X 小时”，**不显示任何倒计时**。

## 12. 审计

`audit_log`：`seq`（单调）、`ts`、`actor_type/actor_id`（user|agent|system）、`action`、`target`、`decision`（ALLOWED|DENIED|HELD|BLOCKED）、`ruleset_version`、`details jsonb`、`prev_hash`、`hash = sha256(prev_hash ‖ canonical(row))`。

- 迁移角色为表 owner，应用角色另建且**只有 INSERT**；并发写入由链头行 `FOR UPDATE` 串行化（或由 sealer 按 `seq` 补 hash），防止 `prev_hash` 分叉；每日末 checkpoint 导出到库外锚定；
- **被拒绝/被阻断的调用也写审计**，且**用独立事务提交**，不随业务事务回滚（INV-11）；
- 保留期与个人信息：本期不进入买家个人信息；导出默认脱敏，**导出动作本身留痕**；
- 审计页标题只承诺“系统的每个决定与人的每次回填都可查”；通道 A 下平台侧实际写入以卖家后台为准（不得写成“每次写都有平台证据”）。
