# 01 · 产品理念与红线

> 本册是实现的宪法。任何代码、画面、接口都不得与本册冲突。

## 0. 现状与痛点（为什么需要它）

> 本节内容来自 DeepSeek 版《产品理念与红线》§2.1 / §2.2，按本版术语改写。放在最前面，是因为「痛点」决定后面所有取舍：不解决这几件事的功能，再漂亮也不做。

### 0.1 痛点：现实长什么样

| 痛点 | 现实 |
|---|---|
| **店多** | 一个店一套后台、一套账号、一套习惯。做 5 个店，等于脑子里跑 5 套流程 |
| **语言多** | 标题要本地化、客服要即时回、退货理由要看懂；日语写得像机器翻的，转化和评分都吃亏 |
| **7×24** | 买家凌晨发消息，平台发货时钟凌晨开始走。人睡觉的时候，指标在扣分 |
| **规则复杂且在变** | 发货时限、差评率、商责退货率、违规分冻结活动资格……规则改了你可能一周后才知道 |
| **数据分散** | 订单在后台、钱在结算单、广告在另一个工具、退货在第三个地方。想算一次真实毛利，要手工拼三天 |
| **容易出错** | 改价少打一个零、批量下架手抖多选、退货地址抄错。这些错误大多**收不回来** |

### 0.2 CrossPilot 怎么解决

| 痛点 | 它是怎么做的 |
|---|---|
| 店多 | 一次操作**可复制到其他店铺**，但先检查目标店是否适用；本期只有 1 家店，所以只做**逐店差异预演 + 导出 B 店上架包**，真正代做随多店进下一阶段 |
| 语言多 | 文案、客服话术自动本地化，本地化结果再过一遍合规校验 |
| 7×24 | 岗位员工不睡觉：人在睡觉时它继续干低风险活，遇到必须人拍板的就**挂着等你醒来** |
| 规则复杂 | 平台规则库带版本、带有效期；规则过期或没覆盖到的动作**一律不放行、交给人** |
| 数据分散 | 所有店铺数据汇总到一套口径里，日/周报自动出 |
| 容易出错 | 高风险动作必须人过手；低风险动作配安全带：执行后留一个可撤回 / 可下架的窗口（下架是**补偿动作**，不是回滚） |

> **一句话对照**：以前是「人操作平台，工具打下手」；现在是「**AI 岗位员工操作平台，人在两个节点签字**」。

## 1. 一句话

**AI 干活，人只做两件事：批，和给方向。**
不可撤回的事、系统拿不准的事，一律停下，打包成一张单子交给人。人批了才动。

## 2. 五条设计原则

| 编号 | 原则 | 落到实现上 |
|---|---|---|
| PR-1 | **人只批与给方向** | 人的入口只有：方向卡、待批单（同意 1 / 同意 2 / 少量例外）、授权清单、规则收紧/放宽。其余步骤没有人工按钮；系统每天统计“人的出手次数与用时”并展示（04 §9） |
| PR-2 | **红绿灯 + 闸门：不可撤回或不确定 → 人** | 动作注册表给每个动作固定一个处置（04 §2）。“不确定”与“判定器自己出错”都等于红灯 |
| PR-3 | **保守为默认：不清楚就不做** | 未登记动作＝最严；规则未验证＝只能更严不能更松；缺数据＝`UNKNOWN`＝停；品类准入用**白名单**（没登记的类目不可选） |
| PR-4 | **一次决定，多店生效（预留）** | 本期只有一家店。只做两件事：业务表带 `shop_id`；动作与规则按“可被另一家店复用”的形态定义。不做任何跨店写入、跨店审批 |
| PR-5 | **每个自动化都配安全带** | 每日上限 / 幅度闸门 / 抽样复核 / 一键降级 / 连续失败熔断 / 速率熔断 / 回滚路径 / 参数核对（批准时与执行时是同一件事）。逐项落地见 04 §8 |

补充的两条**工程立场**（这是 Claude 版新增的，用来保证原则能被真正实现）：

| 编号 | 立场 | 含义 |
|---|---|---|
| PR-6 | **工作流优先，Agent 其次** | 选品→采集→素材→上架是固定流程（有状态机，见 03/04）。LLM 只出现在“写文案、归类、解释、规划派活”这几个步骤里；流程的推进、判定、记账、审批全是普通代码。能写成确定性代码的，不交给 Agent |
| PR-7 | **只做主线，其余变成“一条提醒 + 一个跳转”** | 订单、售后、广告、达人、客服、资金在本期不设计、不实现；系统最多提醒你去 TikTok Shop 后台处理（02 §4） |

## 3. 三条红线（每条都必须有自动化测试）

### RL-1 · 未经人工批准，绝不执行

- 红灯动作在人点头前**不执行**。Agent 不能“先做再报备”，不能“按批准的精神”自己微调参数。
- 批的和做的必须是同一件事：执行前重算**载荷哈希**与**事实快照**，对不上就不执行（见 04 §5）。
- 审批单**不设过期作废**。未决期间一直挂起，既不自动放行，也不自动放弃；只做提醒与升级排序。
- 唯一的退回情形：**前置条件失效**（成本涨了、汇率偏离、素材被改、规则命中新条目、货源价变了）。此时旧单置 `VOID`，**自动生成带差异说明的新单**，重新请人批。
- 测试：INV-1、INV-2、INV-3、AC-03、AC-09。

### RL-2 · Agent 默认没有批准权；人可以把“这一类”授权进清单

- 所有 Agent（含 Pilot）默认无批准权；批准人只能是登记在案的自然人。**没有“机器签”这种东西**（见 10 号决策 ADR-13）。
- 人批准一单时，Owner 角色可以勾选“把这一类加入授权清单”（24 小时后生效）。此后在清单范围内，**系统的确定性代批路径**（不是 LLM Agent）可代批同类单。
- 四条铁律：
  1. **可追溯**：谁加的、何时、依据哪一单、边界是什么；每次代批都记录引用的授权编号。
  2. **随时可撤销**：一键撤销，立即生效，不要理由、不要复核。
  3. **只能收窄，不能放宽**：缩小范围/金额/频次/有效期立即生效；放宽等于新建一条，需人批并写理由，且 24 小时后生效。
  4. **有效期 + 用量上限**：每条必有到期日（≤30 天）与最大次数，到期或被抽检发现问题**自动失效**，不自动续期。
- **永不可授权**（一条都进不了清单）：`ACT-APPROVE-ASSETS`（素材与价格同意）、`ACT-LIST-CREATE`（上架）、`ACT-RELEASE-COST-GATE`（超预算放行）、`ACT-ACK-DISPATCH-RISK`、`ACT-ACCEPT-MISMATCH`、`ACT-LOOSEN-RULE`（放宽规则）、`ACT-CREATE-GRANT`（建授权）、`ACT-ADOPT-WEIGHT-SUGGESTION`；以及 NV-2/NV-3 的任何动作（本来就不存在）。
- 本期**可授权**的只有 `ACT-SELECT`（同意 1，选品），且必须落在包络内（04 §7）。同意 2 永远是人。
- 测试：INV-4、INV-5、INV-6、AC-05、AC-06。

### RL-3 · 判定必须由确定性规则产生，不由 AI 感觉

- 一个动作要不要审批、是否高风险、合规是否通过、利润是否可算、金额多少——**全部由写死的规则与计算得出**。
- LLM 只负责：措辞、归类建议、写方案、解释。LLM **不参与**风险判定、金额计算、规则命中。
- LLM 可以对合规结果**加严**（提出额外 WARN 供人参考），**不可以放宽**任何一条确定性结果。
- Agent 自评“我很有把握”只是给人看的备注，不构成免审批理由。
- **证据由系统按动作类型固定生成**，Agent 只能补充，不能删减或改写。
- **“谁来批”由系统按动作类型推导**，不由 Agent 指定。
- 判定组件自身出错（规则库读不到、规则过期、计算异常）→ 结果为 `HOLD`（等同不确定），**绝不放行**。
- 测试：INV-8、INV-9、INV-10、AC-07、AC-08。

## 4. 永远不做的事（NV）

| 编号 | 不做 | 实现含义 |
|---|---|---|
| NV-1 | 不替客户做税务申报 | 税费只在利润测算里使用，界面标“测算，非申报依据” |
| NV-2 | 不动资金 | 提现、划转、付款周期、保证金操作**没有工具、没有接口、没有按钮**；CI 断言动作注册表中查不到 |
| NV-3 | 不做店铺关闭、主体变更、账号权限变更、申诉提交的自动决策 | 同上，工具不存在 |
| NV-4 | 平台规则以官方为准，不凭记忆写规则 | 规则表必带出处（URL/条款/抓取日期/生效日）；无出处的规则只能是“更严”的保守规则 |
| NV-5 | 不用未授权方式访问平台 | 不做爬虫、不做模拟登录、不用插件绕后台；零接口阶段数据由人导入 |
| NV-6 | 不伪造、不美化 | 不生成买好评/诱导好评话术，不伪装第三方评价，不虚构功能/附属品 |
| NV-7 | 不替人签协议、不代表平台 | 无 |
| NV-8 | 不替人下经营结论 | 没有方向卡就不选品；定价策略、主推品、冲量决定属于人 |
| NV-9 | 不替人承担审批责任 | 批准人必须是自然人；单人运行显式标注并追加补偿措施（04 §10） |

## 5. 不变量（INV）——全部需要自动化测试（INV-17…21 为架构评审后补强）

| 编号 | 不变量 |
|---|---|
| INV-1 | 任何 `ACT-*` 的处置为 REQUIRE_HUMAN 的动作，在没有对应 `APPROVED` 审批单（且未 `VOID`）时，工具层拒绝执行 |
| INV-2 | 审批单不存在“因超时变为通过/拒绝/作废”的状态转换；状态机里没有该边 |
| INV-3 | 执行前重算载荷哈希与事实快照；不一致 → 审批单 `VOID` + 生成新单；不执行 |
| INV-4 | `approver_user_id` 必须指向 `kind='human'` 的用户（复合外键 + `approver_kind='human'` 的 `CHECK`）；`approver_user_id` 与 `delegated_via_grant_id` 恰好一个非空；Agent 不能出现在批准人列 |
| INV-5 | 永不可授权清单中的动作无法写入 `grants.action_type`（枚举约束 + 注册表断言） |
| INV-6 | `grants` 的更新只允许收窄；放宽等于新建（触发器 + 单测）；每条有 `expires_at ≤ now+30d` 与 `max_uses` |
| INV-7 | 动作注册表之外的动作名一律被 Tool Gate **拒绝（`ACTION_FORBIDDEN`）并写审计，不生成审批单** |
| INV-8 | 合规/风险/金额的判定函数不得调用 LLM（静态扫描 + 依赖注入测试：判定模块无 LLM 客户端依赖） |
| INV-9 | 判定器内部异常 → `HOLD`；规则库版本缺失/过期 → `HOLD`；永不返回 ALLOW |
| INV-10 | 任一成本项缺失 → 利润字段为 `UNKNOWN`，候选不进排序，不得进入同意 1 |
| INV-11 | 所有 Tool Gate 调用（含被拒绝的）都有审计行；审计表无 UPDATE/DELETE 权限，且有哈希链 |
| INV-12 | 资金/申诉/关店/税务类动作名在注册表中不存在（NV-2/NV-3） |
| INV-13 | 同一 Agent 7 天内产生 `held_reason='UNSPECIFIED'`（未按枚举上报原因）的挂起 ≥3 次 → 对应能力降级为“只出建议” |
| INV-14 | 已批准素材的任一字符/像素变化 → 新版本，旧批准不适用，重新走同意 2 |
| INV-15 | 通道 A 的“已完成”必须带回填的后台实际值；与批准值不一致 → `READBACK_MISMATCH`，不得置 `LIVE` |
| INV-17 | 执行必须带 `approval_id`，且动作、`subject_refs`（仅 id 列表）、载荷哈希、`shop_id` 逐项一致；批准只能被 CAS 消费一次 |
| INV-18 | 审批单进入 PENDING 后内容不可变；`decide` 必须带版本与载荷哈希 |
| INV-19 | Tool Gate 先 `authorize(actor, action)`：Agent 只能调用 AUTO 且在白名单内的动作；`HUMAN_INITIATED` 只允许匹配角色的自然人 |
| INV-20 | 规则评估为三值；任一 UNKNOWN → HOLD；删除任一必需事实，结果不得是 ALLOW |
| INV-21 | 授权用量原子消费：任意并发下 `used_count ≤ max_uses` 且日用量 ≤ `max_per_day` |
| INV-16 | 日常引用金额的行都带币种与汇率快照编号；`float` 不出现在金额列/计算里 |

## 6. 判定顺序速记（每个动作都按这个顺序）

```
1. 动作在注册表里吗？           否 → DENY（ACTION_FORBIDDEN，不生成审批单）
2. 调用者有权发起吗？(authorize)  否 → 403
   判定器/规则库可用且未过期吗？  否 → HOLD
3. 命中 BLOCK 规则吗？           是 → BLOCK（不进审批，只能改后重来）
4. 有任一必需事实 UNKNOWN 吗？   是 → HOLD（缺口队列：补什么能解锁什么）
5. 注册表处置是 AUTO？           是 → ALLOW_AUTO（留痕、受安全带约束）
6. 否则 → REQUIRE_HUMAN（生成审批单；若在有效授权范围内且动作可授权 → 可由 Pilot 代批）
```
