# #8 的三套方案

> PM Agent 写。固定三套:**V1 是推荐**,V2、V3 是真正不同的做法。
> 评审 Agent 做 D1;人定版时写 `[定版] V<编号> <修改意见>`,没空时 60 分钟后自动按 V1。

## 概要

| 项目 | 内容 |
|---|---|
| Issue | #8 |
| 需求(一句话) | 先做一个能点的应用骨架:今日页 + 候选列表,数字用已合并的成本引擎算 |
| 需人定版 | 否(不删改数据、不对外、不产生费用、不涉及权限) |
| 三套的区别(一句话) | V1 按设计的正式栈(React+Vite) / V2 服务端渲染先跑起来 / V3 纯静态演示页 |

## V1(推荐)

### 功能设计
| 项目 | 内容 |
|---|---|
| 对应的需求 | REQ-8-01 … 05 |
| API | `GET /healthz`;`GET /api/v1/today`(待办数、就绪缺项、样例提醒);`GET /api/v1/candidates`(样例候选 + 成本分项)。均为只读,返回样例数据 |
| 数据 | 仓库内 `backend/data/sample/*.json` 作为样例;不建表、不接数据库(持久化留给下一个 Issue) |
| 处理流程 | 1. 启动 FastAPI → 2. 读样例 JSON → 3. 用 `costing.compute` 算出每个候选的成本与毛利 → 4. 前端 Vite 拉接口渲染 |
| 权限与错误处理 | 不鉴权(本机 127.0.0.1);接口错误返回 `problem+json`;样例缺失时页面显示空态而不是白屏 |
| 影响范围 | 新增 `backend/app/`(FastAPI 入口)、`frontend/`(Vite + React + TS)、`backend/data/sample/`;不动 `crosspilot/` 内核 |
| 估算 | 中,约 16 小时,把握 中 |

### 画面
`V1.html`:今日页(待办、就绪、提醒)、候选列表(表格 + 展开成本)。用 `design/screens/assets/cp2.css` 的风格变量,不引 UI 框架。

### 优点和顾虑
- 优点:一开始就用设计定的栈(React 18 + TS + Vite),后面 10 个画面直接往上加,不用重写前端。
- 顾虑:需要 `npm install`(要联网);首屏比服务端渲染慢一点。

## V2

### 功能设计
| 项目 | 内容 |
|---|---|
| 对应的需求 | REQ-8-01 … 05 |
| API | 同上,但页面由 FastAPI 用 Jinja 模板直接渲染(`GET /`、`GET /candidates`) |
| 数据 | 同 V1 |
| 处理流程 | 模板里直接带出成本分项,不需要前端拉接口 |
| 权限与错误处理 | 同 V1 |
| 影响范围 | 只新增 `backend/app/` 与模板目录,不引入 Node 工具链 |
| 估算 | 小,约 8 小时,把握 高 |

### 画面
同 V1 的两屏,复用原型 CSS。

### 优点和顾虑
- 优点:最快看到画面,不需要 npm,断网也能跑。
- 顾虑:**偏离设计栈**,等做到 10 个画面和交互(同意 1 批量勾选、审批单展开)时几乎肯定要重写成 React——那部分工作白做。

## V3

### 功能设计
| 项目 | 内容 |
|---|---|
| 对应的需求 | REQ-8-01 … 05 |
| API | 只有一个 `GET /api/v1/candidates`;页面是仓库里的静态 HTML + 原生 JS |
| 数据 | 前端直接读同一份 JSON |
| 处理流程 | 打开 `python -m http.server` 即可看 |
| 权限与错误处理 | 无 |
| 影响范围 | 只加 `frontend-demo/` |
| 估算 | 很小,约 4 小时,把握 高 |

### 画面
静态两屏,数据写死。

### 优点和顾虑
- 优点:今天就能看到。
- 顾虑:没有后端,不是"应用的骨架";需求里的 `/healthz`、接口形态都验证不到,基本等于做了一遍原型。
