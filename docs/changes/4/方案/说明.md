> PM Agent 写。固定三套:**V1 是推荐**,V2、V3 是真正不同的做法。
> 评审 Agent 做 D1;人定版时写 `[定版] V<编号> <修改意见>`,没空时 60 分钟后自动按 V1。

## 概要

| 项目 | 内容 |
|---|---|
| Issue | #4 |
| 需求(一句话) | 把 `03 §3.1` 的到岸成本与利润口径写成可复算的确定性代码,利润算不出来时必须 UNKNOWN 并停住(INV-10) |
| 需人定版 | 否(不删改数据、不对外发送、不产生费用、不涉及权限) |
| 三套的区别(一句话) | V1 直白的纯函数:每个成本项一个函数 / V2 配置表驱动:公式与缺失级别写在费率卡里 / V3 依赖图:把每项建成事实节点,按依赖求值 |

## V1(推荐)

### 功能设计
| 项目 | 内容 |
|---|---|
| 对应的需求 | REQ-4-01 … REQ-4-08 |
| API | 无 HTTP 接口。新增模块 `backend/crosspilot/costing/`:<br>`compute(snapshot: CostInput) -> CostResult`;**纯函数**,无 I/O、无时钟、无 LLM(INV-8 同一条约束)。<br>`CostResult`: `items[]`(每项 key/value/unit/source/fetched_at/status/severity)、`revenue`、`profit`、`margin`、`status ∈ COMPUTED\|UNKNOWN`、`missing[]` |
| 数据 | 新增内存结构:`RateCard`(版本 + 每项 `value/source/fetched_at/status/severity`)、`TaxRegime`(枚举 + 有效期)、`FxRate`(`rate/ref_date/source_id`)、`Assumptions`(退货率、`assumed_units_per_order`、预计销量)。**不建表**,持久化随 Issue「数据模型」再做 |
| 处理流程 | 1. 校验必需的 `RateCard` 项是否存在 → 2. 按 c1→c16 顺序求值,每项先判定 `MISSING` → 3. 任一项 `severity=BLOCKING` 且缺失 → 立即返回 `status=UNKNOWN`,`missing` 列出 key → 4. 逐项四舍五入到 JPY 整数 → 5. 求和得 `profit`,`revenue` 与 `profit` 推导 `margin` → 6. `tax_regime=UNKNOWN` 时同样返回 UNKNOWN;`ASSUMED_WORST` 时 `assumed=true` |
| 权限与错误处理 | 纯计算,无权限概念。输入缺项不是异常,是 `UNKNOWN` + `missing[]`;只有编程错误(如金额为 float)抛异常 |
| 影响范围 | 新增 `backend/crosspilot/costing/{__init__,items,result,tax}.py`、`backend/tests/test_inv_10_*.py`、`backend/tests/test_costing_*.py`;`docs/决策/` 加一条「成本口径唯一实现处」。不动现有 `04` 内核 |
| 估算 | 中,约 10 小时,把握 高 |

### 画面
无(本期只做计算内核;成本分项的展示随 SCR-03 的候选详情一起做)

### 优点和顾虑
- 优点:最直接,和设计书 `03 §3.1` 的公式一一对应,评审时能逐行核对;缺失语义集中在 `CostResult` 一处,INV-10 容易测。
- 顾虑:11 个成本项各写一个函数会有重复样板;公式改动要改代码(但公式本来就该由人批才能改)。

## V2

### 功能设计
| 项目 | 内容 |
|---|---|
| 对应的需求 | REQ-4-01 … REQ-4-08 |
| API | `compute(rate_card, snapshot) -> CostResult`,但每项的定义来自 `rate_card.items[key].formula`(受限表达式,只允许 `+ - × ÷`、常数、其他项引用)与 `severity` |
| 数据 | `rate_card` 增加 `formula` 列;新增白名单算子表与求值器(自写的递归下降解析,不 `eval`) |
| 处理流程 | 1. 读表 → 2. 拓扑排序依赖 → 3. 逐项求值 → 4. 缺失按 `severity` 汇总 → 5. 同 V1 |
| 权限与错误处理 | 改公式属于「放宽/收紧」,要走 `ACT-LOOSEN-RULE`;表达式解析失败 → 该项 `UNKNOWN` |
| 影响范围 | 新增表达式引擎与 30+ 个单测,比 V1 多一倍代码;`rate_card` 表结构要提前定 |
| 估算 | 中,约 16 小时,把握 中 |

### 画面
无

### 优点和顾虑
- 优点:费率卡与公式同处一处,非程序员也能改费率口径;多市场时复用。
- 顾虑:多了一个「小型表达式语言」——这是本项目最容易变成过度实现的地方(`00 §4` 要求最小实现);表达式写错时错误信息比 V1 难懂。

## V3

### 功能设计
| 项目 | 内容 |
|---|---|
| 对应的需求 | REQ-4-01 … REQ-4-08 |
| API | `graph = build_graph(); graph.evaluate(facts) -> CostResult`。每个成本项 = 一个 `Fact` 节点(`key`, `requires`, `compute`, `severity`);事实节点可被多个成本项共享 |
| 数据 | 事实注册表 + 依赖图;节点可标注「补哪一项能解锁哪些候选」(直接支撑 CAP-CAN-06 缺口队列) |
| 处理流程 | 1. 建图 → 2. 从叶子节点求值 → 3. 缺事实的节点标 UNKNOWN,并向上传播 → 4. 收集「缺什么」的传递闭包 |
| 权限与错误处理 | 同 V1 |
| 影响范围 | 新增图引擎 + 节点定义 + 传播测试;缺口队列的展示延后到 CAP-CAN-06 |
| 估算 | 大,约 24 小时,把握 中低 |

### 画面
无

### 优点和顾虑
- 优点:天然支持「缺哪项解锁几个候选」,以后加成本项不用改引擎。
- 顾虑:现在就造图,是在为还没到的需求(缺口队列)付结构成本;对 11 个线性成本项属于过度设计。
