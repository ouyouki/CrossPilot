# PR 正文的写法

> 改编自 Matt Pocock 的 skills(MIT,见 `skills/LICENSE-mattpocock-skills.txt`);原版注明:「概要」一节的图示清单几乎原样取自 Dex Horthy(HumanLayer)的 show-me skill(https://github.com/humanlayer/skills)。

PR 正文按 `.github/pull_request_template.md` 写。其中「概要」「证据」「合并风险」三节照下面的写法。不写开场白,文字要短,用 `docs/术语表.md` 里的词。

## 概要

选**最小的**、能把要点说清的图示,放在它说明的那句话旁边。只留回答问题需要的调用、文件、属性、状态、边界。可以用一种,也可以几种,一般不会全用,不要把人淹没。

- 逻辑或算法 → 伪代码:
  ```text
  保存时
    内容没变 → 返回缓存的结果
    写入新内容
    返回新的结果
  ```
- 运行时的调用 → 调用树:
  ```text
  提交表单
    创建会话
      保存请求
      启动处理
    跳到会话画面
  ```
- 画面结构 → 部件树(写上要紧的状态和所在的文件)
- 文件的分工或大的重组 → 浅的目录树(每行一句注释)
- 交互、控制流、数据流 → Mermaid 图(GitHub 能直接显示)
- 重点是"改了什么"、周围的形状已经存在 → 用 `diff` 形式画上面任何一种:
  ```diff
   保存时
  -  写入内容
  +  内容没变 → 返回缓存的结果
  +  写入新内容
  +  让缓存失效
  ```
- 大部分是新的、或省略上下文会看不出归属和顺序时 → 写出整段。

## 证据

证明改动有效的具体证据,改之前和改之后对比:
- **截图最好**(画面有改动时):改之前 / 改之后,确认的地方用红框和编号(和 `04-证据.md` 同样的规则,只用样例数据)。
- **执行结果其次**:测试结果、命令的输出。写出现在从失败变成通过的那个测试(用例 ID 和一句话)。

## 合并风险

- **门**:单向门还是双向门。双向门能退回(撤回 PR 就恢复),单向门退不回(删除或迁移数据、对外发送、改了外部依赖的接口)。撤回代价小的,风险低。
- **影响范围**:一个词概括,再写可能的后果。把可能性都想一遍:布局错位、调用方或使用者受影响、手机宽度、性能、权限、已有数据。和方案的「影响范围」对照。
