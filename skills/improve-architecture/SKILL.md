# 改进代码结构

> 改编自 Matt Pocock 的 skills(improve-codebase-architecture,MIT,见 `skills/LICENSE-mattpocock-skills.txt`)。原版做成 HTML 报告后和用户一问一答;本框架里写成 GitHub 上的报告,最值得做的提成 Issue,做不做由人定版。

找出结构上的摩擦,提出**加深的机会**:把浅模块变成深模块的重构。目的是好测试、Agent 好找。
用语全部照 `skills/codebase-design/SKILL.md`(模块、接口、实现、深度、深、浅、接缝、适配器、杠杆、集中),不说"组件""服务""API""边界"。业务的名字用 `docs/术语表.md` 的。`docs/决策/` 里的决定不重新争论。

## 1. 先定范围,再看(不做用不上的)

加深一个模块的回报是以后改它更容易,所以重点看**最近改得多的地方**:
- `git log --oneline --since=<上次报告的日期> origin/main` 和 `git log --format= --name-only -n 200 origin/main`,找反复出现的文件和目录
  (自己数,不用管道和 sort 等命令:评审 Agent 在无界面运行时只能用读取的 git 命令)。
- 被评审退回、测试退回、`[阻塞]` 多的 Issue 动过的地方(`B gh search issues` / `B gh pr list --state merged --json …`)。
- 改动很分散、没有明显的热点时,再放大范围。

先读 `docs/术语表.md` 和相关的 `docs/决策/`。然后读代码,记下让你觉得别扭的地方(不按死板的规则):
- 理解一个概念要在很多小模块之间跳来跳去?
- 哪里的模块是**浅**的,接口几乎和实现一样复杂?
- 哪里为了测试抽出了纯函数,但真正的 bug 藏在调用它的方式里(没有**集中**)?
- 哪里紧耦合的模块越过接缝互相渗透?
- 哪些部分没有测试,或者通过现在的接口很难测?

对怀疑是浅的东西用**删除测试**:删掉它,复杂度会集中起来,还是只是挪了个地方?"会集中"才是要找的信号。

## 2. 写报告

在「每日计划」Issue 写一条评论,第一行固定 `[架构建议] YYYY-MM-DD`(日期按 `project.toml` 的 `utc_offset`)。没有值得提的也写 `[架构建议] YYYY-MM-DD 本周没有`。
最多 5 个候选,每个一段(GitHub 能直接显示 Mermaid 图,不用外部的脚本和样式):

~~~md
### <候选的短标题,说出加深什么,例「合并订单受理的流水线」>
**推荐度**:强 / 值得研究 / 推测    **依赖的种类**:进程内 / 有本地替身 / 端口和适配器 / 替身
**文件**:`src/…`、`src/…`
**问题**:一句话,哪里难受。
**做法**:一句话,改成什么样。
**收益**:每条不超过 10 个字,用用语表的词,例「集中:bug 集中在一个模块」「杠杆:一个接口,N 个调用处」「删掉 4 个转手的模块」
```mermaid
flowchart LR
  subgraph 之前
    A[订单受理] --> B[订单校验] --> C[订单存储] -.渗透.-> D[价格计算]
  end
  subgraph 之后
    E[订单受理模块(深)]
  end
```
(和 `docs/决策/NNNN` 冲突时:写一行"和决策 NNNN 冲突,但值得重新讨论,因为…";摩擦不够大就不提。)
~~~

最后一节「最先做哪个」:候选名和一句理由。
写法:不写开场白、不写"更好维护""代码更干净"这类空话;能写成一条的就写成一条,能删的就删。**这一步不设计接口**(接口在 Issue 的方案里由 PM 出三套)。

## 3. 提成 Issue(最多 2 个)

推荐度是「强」的,最多 2 个提成 Issue。先搜已有的 `类型:改进`(**开着的和已关闭的都看**:`B gh issue list --state all --label 类型:改进 --json number,title,state`):
同样的主题已经有了就不提;人关闭了的(不做)除非有新的证据,也不再提。

```
B gh issue create --title "[改进] <候选的短标题>" --label 类型:改进 --label 需人定版 --body-file - <<'EOF'
## 目的
<问题和收益,一两句>

## 范围
<涉及的模块和文件;不改的东西>

## 验收条件
- 对外的行为不变(现有的测试和回归清单全部通过)
- <接口变小、测试改在新接口上 等可确认的条件>

来源:「每日计划」的 [架构建议] YYYY-MM-DD
EOF
```

标签只加 `类型:改进` 和 `需人定版`(评审 App 只能建这样的 Issue)。重构不急,做不做由人决定:人看过后加 `状态:待处理`,PM 才会拾取,
之后按普通的需求走(三套方案 → D1 → 人定版 → 开发);不想做的人直接关闭。这样没人要的重构不会消耗 Token。
