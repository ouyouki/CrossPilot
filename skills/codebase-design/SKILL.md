# 模块设计

> 改编自 Matt Pocock 的 skills(MIT,见 `skills/LICENSE-mattpocock-skills.txt`)。

设计**深模块**:小的接口后面有很多行为,放在干净的接缝上,能通过这个接口测试。凡是设计或重组代码的地方都用这套用语和原则。目的:调用方得到杠杆,维护者得到集中,所有人都好测试。

## 用语(照这个用,不要换成"组件""服务""API""边界")

- **模块**:有接口和实现的任何东西,不分大小:函数、类、包、跨层的一块。
- **接口**:调用方要正确使用这个模块必须知道的一切:类型签名,还有不变条件、调用顺序的约束、出错的方式、需要的设置、性能特征。(不只是类型签名。)
- **实现**:模块里面的代码。
- **深度**:接口处的杠杆。调用方(或测试)每学一点接口,能用到多少行为。小接口后面有大量行为 = **深**;接口和实现差不多复杂 = **浅**。
- **接缝**:不改那个地方就能改变行为的位置,也就是模块接口所在的位置。接缝放在哪,本身是一个设计决定。
- **适配器**:在接缝上满足接口的具体东西。说的是它填哪个位置,不是里面有什么。
- **杠杆**:调用方从深度得到的:学得少,能做得多。一份实现,N 个调用处和 M 个测试都受益。
- **集中**:维护者从深度得到的:修改、bug、知识、验证都集中在一处,修一次,处处都好。

## 深和浅

深模块 = 小接口 + 大量实现;浅模块 = 大接口 + 薄薄的实现(只是转一下手,避免)。设计接口时问:
- 能减少方法的数量吗?
- 能简化参数吗?
- 能把更多复杂度藏到里面吗?

## 原则

- **深度是接口的性质,不是实现的。** 深模块内部可以由小的、可替换的部分组成,只是它们不在接口上。模块可以有**内部接缝**(实现私有,自己的测试用)和接口上的**外部接缝**。不要因为测试要用,就把内部接缝露到接口上。
- **删除测试**:想象删掉这个模块。复杂度跟着消失 → 它只是转手;复杂度在 N 个调用方那里重新出现 → 它有存在的价值。
- **接口就是测试面。** 调用方和测试走同一个接缝。想测到接口后面去,说明模块的形状可能不对。
- **一个适配器 = 假想的接缝;两个适配器 = 真的接缝。** 没有真的会变的东西,不要加接缝(通常是"正式 + 测试"两个才算)。

## 为测试而设计

1. **依赖从外面传进来,不在内部创建**:`process_order(order, payment_gateway)`,而不是在里面 `StripeGateway()`。
2. **返回结果,不产生副作用**:`calculate_discount(cart) -> Discount`,而不是 `apply_discount(cart)` 直接改 `cart.total`。
3. **接口小**:方法少 = 要写的测试少;参数少 = 测试的准备简单。

## 加深一组浅模块时:按依赖的种类决定怎么测

1. **进程内**(纯计算、内存里的状态、没有 I/O):总是可以合并,直接通过新接口测,不需要适配器。
2. **有本地替身**(测试用的数据库、内存文件系统):有替身就可以加深,测试里跑替身。接缝在内部,接口上不露出。
3. **远程但是自己的**(自己的其他服务):在接缝定义一个**端口**(接口),逻辑留在深模块里,通信方式作为适配器注入。测试用内存适配器,正式用 HTTP / 队列适配器。
4. **真正的外部**(第三方服务):把外部依赖作为注入的端口,测试给一个替身适配器。

测试策略:**替换,不叠加**。加深后的模块接口上有了测试,原来对浅模块的单元测试就是浪费,删掉(但不删 03 里有用例 ID 的测试;要删就改 03 并重新做 D2)。测试断言通过接口看到的结果,不断言内部状态;实现变了测试也要变,说明它测到接口后面去了。

## 同一个接口设计两次

第一个想法很少是最好的。接口拿不准时,在 `02-设计.md` 里写出 **2〜3 个真正不同的接口**(不开子 Agent,自己写),每个写:
1. 接口(类型、方法、参数,加上不变条件、顺序、出错方式)
2. 调用方怎么用的例子
3. 实现藏在接缝后面的东西
4. 依赖的种类和适配器(上一节)
5. 取舍:哪里杠杆大、哪里薄

可以从这几个方向出发:接口最小(1〜3 个入口)/ 最灵活 / 让最常见的调用最简单 / 跨接缝的依赖用端口和适配器。
按**深度**、**集中**、**接缝的位置**比较,写出你推荐哪个、为什么;能组合的就提出组合。要有明确的判断,不要只列选项。

## 评审时(D3)看什么

- 新加的模块通得过删除测试吗?只有一个适配器的接缝、只有一个实现的接口、只有一个调用方的层,是不是多余的(过度实现也退回)?
- 测试是在接口上测行为,还是测到了实现细节?
- 依赖是传进来的吗?副作用能不能变成返回值?
