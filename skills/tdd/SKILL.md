# 测试驱动开发(TDD)

> 改编自 Matt Pocock 的 skills(MIT,见 `skills/LICENSE-mattpocock-skills.txt`)。

TDD 是"红 → 绿"的循环:先写一个失败的测试(红),再写刚好让它通过的代码(绿)。下面每一节在每一轮都适用,写测试之前和写的过程中都要对照,不是写完再看。

开始前读 `docs/术语表.md`(有的话),测试名和接口用语和项目的业务用语一致;动到的地方有 `docs/决策/` 里的决定时遵守它。

## 好的测试是什么

测试通过**公开的接口**验证**行为**,不验证内部实现。代码可以整个重写,测试不该跟着变。好的测试读起来像规格:"购物车有效时用户能结账"——一看就知道有什么能力,重构也不会坏,因为它不关心内部结构。

```python
# 好:验证看得到的行为
def test_TC_3_01_user_can_checkout_with_valid_cart():   # TC-3-01
    cart = create_cart(); cart.add(product)
    assert checkout(cart, payment).status == "confirmed"

# 坏:验证实现细节(内部调用了什么)
def test_checkout_calls_payment_service(mocker):
    m = mocker.patch("app.payment_service.process")
    checkout(cart, payment)
    m.assert_called_with(cart.total)

# 坏:绕过接口去验证(直接查数据库)
def test_create_user_saves_row():
    create_user(name="样例")
    assert db.query("SELECT * FROM users WHERE name = ?", ["样例"])

# 好:通过接口验证
def test_create_user_makes_user_retrievable():
    user = create_user(name="样例")
    assert get_user(user.id).name == "样例"
```

好测试的特点:测调用方关心的行为;只用公开的接口;内部重构后仍然通过;写的是"做什么"不是"怎么做";一个测试一个逻辑上的断言。
危险信号:替身换掉了内部的协作者;测私有方法;断言调用的次数或顺序;行为没变一重构就坏;测试名写的是"怎么做";绕过接口去验证。

## 接缝:测试放在哪

**接缝**是测试所在的公开边界:在这里能观察到行为,不用伸进内部。测试只放在接缝上,不针对内部。

**只在事先定好的接缝上测。** 本框架里接缝已经定好:`02-设计.md` 的接口(API、画面、模块的公开函数)和 D2 通过的 `03-测试用例.md`。
- 每个用例对应一个接缝;写测试前,在 `02-设计.md` 或提交说明里写下"这个用例测哪个接缝、能抓到什么、抓不到什么"(一行)。
- 03 里没有、而你觉得必须测的接缝:不要自己加范围外的测试,写 `[提问]`(要改 03 就要重新做 D2)。
- 接口本身的形状拿不准(模块该多深、接缝放哪、接口该露出什么)时,读 `skills/codebase-design/SKILL.md`。

## 反面做法

- **和实现绑在一起**:替身(mock)换掉了内部的协作者、测试私有方法、绕到旁边去验证(查数据库而不是用接口)。特征:行为没变,一重构测试就坏。
- **同义反复**:断言里用和代码一样的算法重算期望值(`assert add(a, b) == a + b`、手算出来的同样的快照、一个常量断言等于它自己),永远会通过,永远不会和代码有分歧。期望值必须来自独立的依据:已知正确的具体值、算过的例子、01 的验收条件。
- **横向切片**:先写完所有测试,再写所有实现。批量写的测试验证的是**想象中**的行为,测的是形状而不是用户看到的行为,对真实的变化不敏感。改用**纵向切片**:一个测试 → 一个实现 → 再来,每个测试根据上一轮学到的东西来写。

## 什么时候用替身(mock)

只在**系统边界**用:外部 API(支付、邮件等)、数据库(能用测试库就用测试库)、时间和随机数、文件系统(有时)。
不对自己的类和模块、内部协作者、自己能控制的东西用替身。

在系统边界上,把接口设计得容易替换:
- **依赖从外面传进来**,不在内部创建(`process_payment(order, payment_client)`,而不是在函数里 `StripeClient(...)`)。
- **每个外部操作一个函数**(`get_user(id)`、`create_order(data)`),不要一个通用的 `fetch(endpoint, options)`——这样每个替身只返回一种形状,测试的准备里没有条件分支。

## 循环的规则

- **先红后绿。** 先写失败的测试,看它失败,再只写让它通过的代码。不预先写以后的测试,不加推测出来的功能。
- **一次一小块。** 每一轮:一个接缝、一个测试、一个最小的实现。
- **重构不在循环里。** 不混进"红 → 绿"。评审 Agent 在 D3 按 `skills/codebase-design/SKILL.md` 指出要重构的地方,开发 Agent 在退回后的修改里做(测试保持绿)。

## 本框架的要求

- 自动用例的测试名或注释里写**用例 ID**(例 `# TC-3-01`),CI 的 trace 靠它对应。
- 画面的用例写成 E2E 测试(Playwright 等),同样写用例 ID。
- 全部用例变绿后,跑 `project.toml` 的 `[checks]`(全量回归),再提 PR。
