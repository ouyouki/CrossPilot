# 给 Agent 写文件(人用)

> 改编自 Matt Pocock 的 skills(writing-for-agents,MIT,见 `skills/LICENSE-mattpocock-skills.txt`)。

**给人用的**:你根据 `/retro` 或评审的建议改 `agents/*.md`、`commands/*.md`、`skills/*/SKILL.md`、`AGENTS.md` 时,让 AI 按这里的要点检查。
改完运行 `python scripts/dev/gen_adapters.py` 生成两种 harness 的文件,再跑 `bash tests/selftest.sh`(这些文件的改动要你批准,CODEOWNERS)。

目标不是"每次输出一样",而是**每次走同样的过程**。

## 1. 指针:决定 Agent 什么时候去读
Agent 一直看得到的那一行(skill 的 `description`、`AGENTS.md` 里提到某个文件的一句、`agents/*.md` 里"读 skills/…"的一句)就是**指针**。
什么时候去读,取决于指针的措辞,不取决于被指的内容有多重要。重要的内容没被读到时,先把指针写清楚,不行再把内容搬进来。
- 关键词放在前面。
- 每种情况写一个触发条件;同一种情况的近义词合成一个。
- 指针里不重复正文已经有的东西(一直加载的每个字都花 Token)。

## 2. 两种负担
- **上下文负担**:一直加载的内容(`AGENTS.md`、各 Agent 的正文、skill 的 description)每一轮都占 Token 和注意力。
- **人的负担**:没有指针的内容,只能靠人记得"有这个文件,什么时候用"。值得花在需要人判断的地方,别处去掉。

## 3. 内容放在哪一层
文件里只有两种内容:**步骤**(按顺序做的事)和**参考**(规则、定义,需要时查)。按 Agent 多急着要排:
1. 文件里的步骤;
2. 文件里的参考;
3. 拆出去的参考(另一个文件,靠指针读到)。
放上层的太多,步骤会被淹没,Agent 漏做;推下去的太多,该看的看不到。判断方法:**每条路径都要的放在文件里,只有部分情况要的推出去**。
同一个概念的定义、规则、例外放在同一个标题下,不要散在几处。文件太长时,即使每行都有用,注意力也会被摊薄,这时按情况或按顺序拆开。

## 4. 每一步都有"做完"的标准
- **清楚**:Agent 分得清做完和没做完。"理解了"这种模糊的标准会让 Agent 急着结束,去做后面的步骤。先把标准写清楚;实在写不清又看到它在赶,再把后面的步骤拆到另一个命令里(本框架的命令之间本来就是分开的会话)。
- **要求的量**:"每个改过的模型都核对过"比"列出改动"逼出更多的工作。能检查、又要求全部做到的标准最好。

## 5. 关键词
用一个模型本来就懂的词代替一串描述(例:"红"代替"能稳定复现这个问题的检查失败了")。在正文里反复用同一个词,不要每次换说法。
先找现成的词;自己造词要先定义清楚,因为它不会唤起模型已有的理解。

**少用"不要"**:写"不要做 X"反而让 X 更显眼。尽量写要做的事("评论只写一行")。只有无法正面表达的硬性规定才用"不要",并且同时写出该做什么。

## 6. 删减
- 一个意思只写在一个地方。同样的规则写两遍,改一处忘一处,也浪费 Token。
- 环境本身就是依据(`project.toml`、目录结构、`--help` 的输出)。文件里抄一遍就是缓存,会过时;只有查起来代价高时才值得留。
  要写的是 Agent 看环境看不出来的:没写下来的约定、做法背后的理由、配置里看不出的坑。一个文件、一条命令就能查到的,留给环境。
- 每一行都问:它还影响 Agent 的行为吗?不再相关、已经过时的删掉,不要因为"删了怕出事"留成一层层的沉积。
- 逐句检查"空话":模型默认就会做的事(例"要仔细")写了等于没写,整句删掉;如果确实需要更强的要求,换一个更强的词。

## 本框架里的对应
| 原理 | 本框架里 |
|---|---|
| 指针 | 各 skill 的 `description`、`agents/*.md` 里"读 `skills/…`"的句子、`AGENTS.md` 的清单 |
| 步骤 / 参考 | `agents/*.md` 的各个命令小节是步骤;`docs/运营规则.md` 是参考的正本 |
| 拆出去的参考 | `skills/*/SKILL.md`、`docs/templates/` |
| 一个意思只写一处 | 规则只在 `docs/运营规则.md`;Agent 文件写"见 X 章",不抄规则 |
