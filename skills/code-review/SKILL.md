# 两个方向的代码评审(D3)

> 改编自 Matt Pocock 的 skills(code-review,MIT,见 `skills/LICENSE-mattpocock-skills.txt`)。原版用两个并行的子 Agent;本框架里评审 Agent 按顺序做两遍(省 Token),但两遍的结论分开写。

一个改动可能**符合规范却做错了事**,也可能**做对了事却破坏了规范**。分开评审,一个方向的"好"才不会掩盖另一个方向的问题。

## 1. 确定对象
- 差异:`git diff origin/main...origin/<分支>`(三个点 = 和分叉点比较),提交列表:`git log origin/main..origin/<分支> --oneline`。
- 差异是空的、分支取不到时,停在这里,退回并写明原因。

## 2. 规范这一遍
依据(全部读):`AGENTS.md`、`docs/运营规则.md`、`docs/术语表.md`、`docs/决策/`、仓库里写编码规则的文件(有 `CONTRIBUTING.md`、`CODING_STANDARDS.md`、lint 的设置就算)。
工具已经检查的(lint、格式、类型检查)不再重复。

除了仓库写下的规则,再对照下面这组**坏味道**(出自 Fowler《重构》第 3 章)。两条约束:
- **仓库的规则优先**:仓库明确认可的写法,就不当作坏味道。
- **只是判断**:写成"可能是 Feature Envy",不当作硬性违规。

| 坏味道 | 是什么 | 怎么改 |
|---|---|---|
| 名不副实 | 名字看不出做什么或装着什么 | 改名;起不出诚实的名字,说明设计本身不清楚 |
| 重复代码 | 同样的逻辑出现在差异的多处 | 抽出共同的部分,两处都调用 |
| 依恋情结(Feature Envy) | 方法用别的对象的数据比用自己的多 | 把方法移到那份数据旁边 |
| 数据泥团 | 同几个字段或参数总是一起出现 | 合成一个类型,传它 |
| 基本类型偏执 | 用字符串、数字代替一个业务概念 | 给这个概念一个小类型 |
| 重复的分支 | 对同一个类型的 switch / if 链在多处出现 | 用多态,或两处共用一张表 |
| 霰弹式修改 | 一个逻辑改动要改很多文件 | 把一起变的东西收进一个模块 |
| 发散式变化 | 一个文件因几个不相关的理由被改 | 拆开,每个模块只为一个理由变 |
| 夸夸其谈的通用性 | 为需求里没有的情况加的抽象、参数、钩子 | 删掉,等真有需要再加 |
| 过长的调用链 | `a.b().c().d()`,调用方依赖了一路的结构 | 在第一个对象上提供一个方法 |
| 中间人 | 一个类或函数几乎只是转手 | 去掉,直接调用真正的对象 |
| 被拒绝的遗赠 | 子类或实现类忽略或改写了继承来的大部分东西 | 不用继承,改用组合 |

记录:每条写 文件:行、违反了哪条规则(规范文件 + 那一条)或哪种坏味道、引用那段差异。分清**硬性违规**(写下的规则)和**判断**(坏味道)。

## 3. 需求这一遍
依据:Issue 上定版的方案(`docs/changes/<编号>/方案/` 里定版的那一套)、`01-需求.md`、`02-设计.md`、`03-测试用例.md`。
找三类问题,每条引用依据的原文(REQ 编号或方案的句子):
- **缺**:要求了但没做或只做了一部分;
- **多**:差异里有需求没要的行为(范围蔓延);
- **错**:看起来做了,但做法不对(边界、权限、错误处理、数据)。

## 4. 写结论
D3 的正式评审正文里分两节 `## 规范`、`## 需求`,各自列出发现,**不合并、不重新排序**。
最后一行:每个方向的发现数和最严重的一条(各写各的,不在两个方向之间选"最严重")。
- 硬性违规、需求的「缺」「错」 → 退回。
- 只有坏味道(判断)或很小的「多」 → 可以通过,在正文里列出,开发 Agent 下次改动时参考。
