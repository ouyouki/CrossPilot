# 整理成需求(人用)

> 改编自 Matt Pocock 的 skills(to-spec,MIT,见 `skills/LICENSE-mattpocock-skills.txt`)。原版直接发到课题管理;本框架里只输出内容,由人确认后提交。

**给人用的**:通常接在 `skills/grill-me/SKILL.md` 之后。之后由 PM Agent 拾取,出三套方案。

## 做法(给帮你的 AI)

**不再追问**,只把已经讨论过的内容整理出来。
1. 看一下仓库的现状(已有的功能、`docs/术语表.md`、`docs/决策/`),全文用术语表的词,遵守已有的决定。
2. 按下面的格式写出来,给人看。**不要自己提交 Issue**:人确认后,用表单(`.github/ISSUE_TEMPLATE/需求.yml`)提交(表单没有的两节「补充」贴在「范围」的最后);
   或者人明确说"帮我提交"时,用人自己的 gh 提交(先把命令和内容给人看):
   `gh issue create --title "[需求] <一句话>" --label 类型:需求 --label 状态:待处理 --body-file <整理好的文件>`
   (没有 `状态:待处理`,PM Agent 不会拾取)。
3. 只写需求,不写实现的细节(模块、文件路径、代码)——实现由 PM Agent 在方案里出三套。
4. 不写客户名、人名、密钥(用角色,例子用样例数据)。

```md
### 目的
<用户遇到的问题,从用户的角度;为了谁、解决什么>

### 范围
做:
- …
不做:
- …

### 验收条件
<怎样算完成,写成在画面上能确认的形式>
- [ ] …

### 优先级
高 / 中 / 低

### 补充(用户故事)
1. 作为 <角色>,我想要 <功能>,以便 <好处>
2. …
(尽量列全,覆盖这个需求的各个方面)

### 补充(已经定下来的事)
- <讨论中定下来的业务规则、边界情况的处理;原型里得出的决定可以摘关键部分>
```

需求太大(一天做不完)也没关系,PM Agent 会拆成子 Issue。
