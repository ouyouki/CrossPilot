# 原型

> 改编自 Matt Pocock 的 skills(MIT,见 `skills/LICENSE-mattpocock-skills.txt`)。

原型是**回答一个问题的、用完就丢的代码**。问题决定形状:
- **"这个逻辑 / 状态模型对吗?"** → 本文的「逻辑原型」:一个单独的 HTML 文件,能自由点按钮、也能按场景一步步走,把纸上难想清楚的情况推一遍,不懂开发的人也能操作。
- **"画面应该是什么样?"** → 用方案套件做 `方案/V1.html`〜`V3.html`(`python scripts/design/new_proposal.py`)。三套要**结构上**不同(布局、信息的主次、主要操作),不是只换颜色或文字。

问题两种都像时:后端的处理 → 逻辑原型;画面或部件 → 画面方案。在原型的开头写明你的判断。

## 共同的规则

1. **一开始就是一次性的,并且标明。** 放在 `docs/changes/<编号>/方案/原型-<英文短名>.html`,文件名和页面标题都写"原型"。不放进 `src/`,不合进正式代码。
2. **打开就能用。** 一个文件,双击用浏览器打开;不用框架、不用打包、不用服务器,所有东西内联,不加载外部文件。
3. **默认不存数据。** 状态在内存里。
4. **不打磨。** 不写测试,错误处理只到能跑为止,不做抽象。目的是快点学到东西。
5. **把状态摆出来。** 每次操作后,把相关的完整状态显示出来,看得出变了什么。
6. **收下结论。** 原型回答了问题后,把结论(问题和答案)写进 `方案/说明.md` 的功能设计;验证过的逻辑在定版后由开发 Agent 写进正式代码(重写,加测试)。

## 逻辑原型的做法

1. **写明问题**:代码之前,在页面顶部(看得见的介绍,不只是注释)用一段话写清:原型的是什么状态模型、要回答什么问题。
2. **逻辑放在一个可以搬走的纯模块里**:回答问题的那部分逻辑写在一个 `<script>` 里,做成小的纯模块,以后能原样搬进正式代码。页面是一次性的,这个模块不是。形状按问题选:
   - 纯的 reducer `(state, action) => state`:动作是离散的事件、状态是一个值时。
   - 状态机(明确的状态和迁移):"现在哪些操作是合法的"本身就是问题的一部分时。
   - 几个纯函数:没有隐含的"当前状态",只是数据的变换时。
   模块要纯:不碰 DOM、`document`、按钮的处理函数。页面调用它,反过来不行。
3. **页面写给不懂开发的人**:所有文字用业务用语(`docs/术语表.md`),按钮和状态读起来像业务,不像代码。从上到下:
   1. 标题和一句话说明(第 1 步的问题)
   2. **当前状态**:可读的面板(有标签的字段,不是原样的 JSON),每次点击后重画,标出刚变的地方
   3. **自由操作的按钮**:每个动作一个,随时可点,任意顺序
   4. **场景演示**:每个场景一个标签页,写清场景和要注意看什么,下面是按顺序要点的按钮(每一步都是真的按钮,点了就执行并进入下一步);开始一个场景时重置到固定的初始状态。场景选难想清楚的:正常流程、棘手的边界、应该被禁止的操作。
   样式干净克制:清楚的字体、留白、一个强调色,浅色 / 深色都能看。不要动画和花样。
4. **用它发现问题**:自己按场景走一遍;"这不该能做到""我以为 X 会不一样"就是**想法里的 bug**,这正是原型的价值。把发现写进方案。

## 反面做法

- 给原型写测试(要测试的就不是原型了)
- 连真正的数据库
- 泛化("以后要支持 X 怎么办"),原型只回答一个问题
- 逻辑和页面混在一起(纯模块引用了 DOM 就搬不走了)
- 用框架、打包工具、服务器
- 把原型的页面放进正式代码
