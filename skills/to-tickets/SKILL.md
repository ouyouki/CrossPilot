# 拆成子 Issue

> 改编自 Matt Pocock 的 skills(to-tickets,MIT,见 `skills/LICENSE-mattpocock-skills.txt`)。原版拆好后先问用户;本框架里 PM Agent 自己判断,拆分结果写在父 Issue 上,人在方案阶段能看到。

## 1. 收集背景

读父 Issue 的正文和全部评论、`docs/术语表.md`、相关的 `docs/决策/`。看一下现在的代码,找**先整理(预重构)**的机会:"先让改动变容易,再做容易的改动"。

## 2. 拆成纵向切片

- 每个切片从头到尾打通一条窄但**完整**的路径(数据、处理、画面、测试),是**纵向**的,不是"只做数据库这一层"这种横向的。
- 做完的切片**能单独演示或验证**(有自己的验收条件)。
- 每个切片的大小:开发 Agent 一个工作日做得完(开发 Agent 每次运行只做一步,一个切片会跨几次运行)。
- 需要的预重构放在最前面,作为单独的切片。

给每个切片写**依赖**:哪些子 Issue 完成之后它才能开始。没有依赖的可以马上开始。

**大范围的机械改动是例外**(改一个列名、改一个到处用的类型,一改就让成百上千个调用处同时坏掉,没有哪个纵向切片能保持测试通过):按**先扩展、再迁移、后收缩**排:
1. 扩展:新的形式和旧的并存,什么都不坏。
2. 迁移:按影响范围分批(每个包、每个目录)把调用处换过去,每批一个子 Issue,依赖第 1 步;旧的还在,所以每批都能保持测试通过。
3. 收缩:没有调用方了再删掉旧的形式,依赖所有的迁移批次。

各批次单独做不到测试全绿时:仍按这个顺序建子 Issue,但不要分别合并——在父 Issue 上写 `[提问]` 交给人决定合并的方式(本框架一个 Issue 一个 PR,
共用的集成分支不在自动流程里)。

## 3. 建子 Issue(按依赖的顺序,被依赖的先建)

```
B gh issue create --title "[需求] <切片的短名>" --label 类型:需求 --label 状态:待处理 --body-file - <<'EOF'
父 Issue: #<父的编号>
依赖: #<编号>, #<编号>

## 目的
<这个切片让用户能做到什么(从用户的角度),不是按层列出的实现清单>

## 范围
<做的和不做的>

## 验收条件
- [ ] …
- [ ] …
EOF
```

- `依赖:` 这一行的格式固定,行首就是「依赖:」(调度靠它判断:依赖的 Issue 还没合并时,不开始开发这个子 Issue)。没有依赖就写 `依赖: 无`。
- 不写具体的文件路径和代码片段(很快就过时)。例外:原型里得出的、比文字更准确的决定(状态机、数据形状),可以只摘关键部分写进去,注明来自原型。
- 父 Issue 带 `需人定版` 时,涉及那部分的子 Issue 也加 `需人定版`。

## 4. 在父 Issue 上写清楚

写一条评论:拆成了哪些子 Issue(编号、短名、依赖、各自交付什么),先做哪个。去掉父 Issue 的 `状态:…` 标签(父 Issue 由人在子 Issue 都上线后关闭)。不改父 Issue 的正文。
