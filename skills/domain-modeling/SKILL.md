# 领域模型

> 改编自 Matt Pocock 的 skills(MIT,见 `skills/LICENSE-mattpocock-skills.txt`)。

设计时主动建立和打磨项目的领域模型:挑出模糊的词、设想边界场景、把定下来的用语和决定**当场**写下来。(只是**读**术语表来统一用词,任何 Agent 都该做,不需要这个方法;这个方法是用在**改变**模型的时候。)

## 文件

```
docs/
├── 术语表.md                    ← 业务用语(只有一份)
└── 决策/
    ├── 0001-<英文短名>.md        ← 设计决定(ADR)
    └── 0002-<英文短名>.md
```

用到时才建:第一个用语定下来时建 `docs/术语表.md`,第一个决定要记时建 `docs/决策/`。这两处不用写进 `范围.txt`(CI 的 scope 总是允许)。

## 出方案时怎么做

- **对照代码**:需求或方案里描述现有的行为时,到代码里确认是不是这样;不一致就指出来("需求说取消后全额退款,但现在的代码只退一部分,是哪个?")。
- **对照术语表**:需求或自己的方案里用的词和 `docs/术语表.md` 冲突时,马上指出并定下来:"术语表里'取消'是 X,这里的意思像是 Y,是哪个?" 自己定不了的,写进 `说明.md` 的「要人回答的问题」(推荐的答案在前)。
- **把模糊的词改准**:"账户"是指客户还是登录用户?这是两个东西,选一个准确的词。
- **用具体场景检验**:设想边界场景("同一个订单取消后又付款会怎样?"),逼出模型里没想清楚的地方,写进方案的功能设计。
- **当场更新术语表**:一个用语定下来就写进去,不攒着。
- 术语表**完全不写实现的细节**。它不是规格、不是草稿本、不是放实现决定的地方,只是术语表。

## 术语表的格式

```md
# <业务领域的名字>

<一两句话:这个领域是什么、为什么存在。>

## 用语

**订单**:
客户下的一次购买请求,包含商品、数量和送货地址。
_不用_:购买、交易

**发票**:
发货后发给客户的付款请求。
_不用_:账单、付款请求
```

规则:
- **要有主见**:同一个概念有几个词时,选最好的一个,其他的写在「不用」里。
- **定义要短**:一两句话。写它**是什么**,不写它做什么。
- **只收这个项目特有的概念**。超时、错误类型这类一般的编程概念,项目用得再多也不收。
- 自然形成几组时用小标题分组。

## 设计决定(ADR):少写

三个条件**都满足**时才写:
1. **难以撤回**:以后改主意的代价不小
2. **没有背景会觉得意外**:以后的人看代码会想"为什么这样做?"
3. **真的有取舍**:有真正的其他选择,因为具体的理由选了这个

缺一个就不写。值得写的例子:架构的形状;各部分之间的集成方式;有锁定效应的技术选型(数据库、消息队列、认证服务、部署目标——不是每个库);边界和范围的决定(明确"不做"的和"做"的一样有价值);故意偏离常见做法的地方;代码里看不出来的约束(合规、对外的响应时间);不显然的被否定的选项。

格式(编号:看 `docs/决策/` 里最大的编号加一):

```md
# <决定的短标题>

<一到三句话:背景、决定了什么、为什么。>
```

一段话就够。需要时才加:状态(提议 / 采用 / 废弃 / 被 NNNN 取代)、考虑过的选项、后果。

## 本框架里

- PM Agent:出方案时做上面的事;决定写在方案的分支上,和方案一起提交。功能设计里用术语表的词。
- 评审 Agent(D1):方案里的用词和术语表一致吗?该写的决定写了吗?不该写的(容易撤回、显而易见)写了吗?
- 开发、测试 Agent:只读术语表,代码、测试名、文档用同样的词。
