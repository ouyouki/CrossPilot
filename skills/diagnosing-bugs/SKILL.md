# 排查 bug

> 改编自 Matt Pocock 的 skills(MIT,见 `skills/LICENSE-mattpocock-skills.txt`)。

排查难的 bug 的纪律。跳过哪个阶段,都要写明理由。
开始前读 `docs/术语表.md`(有的话)弄清相关模块,看动到的地方有没有 `docs/决策/` 里的决定。

## 先遮住密钥

这个步骤要你把命令、输出、抓到的数据写进评论或日志。**先把所有密钥换成 `<REDACTED>`**。检查手段从环境变量读凭据,凭据留在环境里,不出现在你写出来的东西里。抓到的请求带着认证头:只引用有信号的那几行。
遮住之后信息不够诊断时,说明需要什么(不在评论里贴密钥)。按你的角色升级:开发 Agent 在 Issue 上写 `[提问]` 并加 `待回答`;测试 Agent 写进 `[测试-退回]` 的正文;集成 Agent 在「每日计划」写 `[阻塞]`。

## 第 1 阶段:造一个检查手段(最重要)

**这就是这个方法的核心**,其余都是机械的。有了一个**紧的**通过 / 失败信号(只对**这个** bug 变红),原因一定找得到;二分、验证假设、加日志都只是在用它。没有它,盯着代码看多久都没用。在这里多花力气,有创意,不放弃。

### 造法(大致按这个顺序)

1. **失败的测试**,放在能碰到 bug 的接缝上:单元、集成、E2E。
2. **HTTP 脚本**(curl 等)打一次性环境里跑着的服务。
3. **命令行调用**,用固定的输入,把输出和已知正确的结果比较。
4. **无界面浏览器脚本**(Playwright 等)操作画面,对 DOM、控制台、网络做断言。
5. **重放抓到的数据**:把真实的请求、数据、事件日志存下来(只用样例数据),单独喂给那段代码。
6. **一次性的小环境**:只起系统的一小部分(一个服务,依赖用替身),一个函数调用就走到 bug 的路径。
7. **随机输入循环**:"有时结果不对"的 bug,跑 1000 个随机输入找出失败的模式。
8. **二分**:bug 出现在两个已知状态之间(提交、数据、版本),把"切到状态 X、检查"自动化,用 `git bisect run`。
9. **对比**:同一个输入分别跑旧版本和新版本(或两种设置),比较输出。

本框架里 Agent 在无人看管时运行,**不使用需要人点击的检查手段**。

### 收紧

把检查手段当产品:能更快吗(缓存准备、跳过无关的初始化、缩小测试范围)?信号能更准吗(断言具体的症状,不是"没崩")?能更确定吗(固定时间、固定随机种子、隔离文件系统、断开网络)?
30 秒还时好时坏的检查手段,比没有好不了多少;2 秒、每次结果一样的,才算紧。

### 不稳定的 bug

目标不是干净的重现,而是**更高的重现率**:触发 100 次、并行、加压、缩小时间窗口、插入等待。50% 重现的 bug 能查,1% 的不能,一直提高到能查为止。

### 真的造不出来时

停下,明说。列出试过的办法。按你的角色升级:开发 Agent 在 Issue 上写 `[提问]` 并加 `待回答`;测试 Agent 写进 `[测试-退回]` 的正文;集成 Agent 在「每日计划」写 `[阻塞]`。说明需要:(a) 能重现的环境,(b) 遮好密钥的抓取数据(日志、请求记录),或 (c) 允许临时加日志。**没有检查手段就不进入假设阶段。**

### 完成条件:一个会变红的紧的检查手段

能说出**一条命令**(脚本路径、测试命令、curl),**已经实际跑过至少一次**(在评论或日志里写出命令和遮好密钥的输出),而且:
- [ ] **能变红**:走的是真正有 bug 的代码路径,断言的是**报告的那个症状**,修好后会变绿。不是"跑起来不报错"。
- [ ] **确定**:每次结果一样(不稳定的 bug:重现率固定且够高)。
- [ ] **快**:几秒,不是几分钟。
- [ ] **Agent 能自己跑**:不需要人。

还没有这条命令就开始读代码猜原因时,**停下:直接跳到假设正是这个方法要防止的错误。**

## 第 2 阶段:重现并缩小

跑检查手段,看它在 bug 出现时变红。确认:
- [ ] 失败的是**报告的那个**症状,不是旁边恰好也有的另一个失败。bug 不对,修也不对。
- [ ] 多次都能重现(或重现率够高)。
- [ ] 记下了确切的症状(错误信息、错的输出、慢了多少),后面用来确认修好的就是它。

**缩小**:变红后,把重现缩到**仍然变红的最小场景**。一次去掉一个输入、调用方、设置、数据、步骤,每去掉一个就再跑一次,只留下对失败必要的东西。缩小后,假设的范围变小,也直接变成干净的回归测试。
完成条件:**剩下的每个元素都必要**,去掉任何一个都会变绿。
**没有重现并缩小,不进入下一阶段。**

## 第 3 阶段:提假设

测试任何一个之前,先列出 **3〜5 个排好顺序的假设**。只想一个,会被第一个看起来合理的想法套住。
每个假设都要**能被推翻**,写出它的预测:
> "如果原因是 <X>,那么改 <Y> 会让 bug 消失 / 改 <Z> 会让它更严重。"

写不出预测的假设只是感觉,丢掉或改准。
把列表写成 PR 或 Issue 上的一条普通评论(第一行写「假设(按这个顺序验证)」,**不要**用 `[进度]` 等标记,调度和 CI 会按标记判断)。不用等回复,按自己的顺序继续;PM 或人知道背景的话会补充。

## 第 4 阶段:验证

每个探查都对应第 3 阶段的一个预测。**一次只改一个变量。**
- 首选调试器或交互式检查(环境支持的话),一个断点胜过十条日志。
- 其次是在能区分假设的边界上加**有针对性的日志**。
- 不要"全部打日志然后搜"。

**每条调试日志都加唯一前缀**,例 `[DEBUG-a4f2]`,最后一条 `grep` 就能清干净。

**性能问题**:日志通常没用。先建立基准测量(计时、性能分析、查询计划),再二分。先量,再修。

## 第 5 阶段:修复 + 回归测试

**修复之前**先写回归测试,但只在有**正确的接缝**时写。正确的接缝是:测试能重现调用处真实的 bug 模式。能用的接缝太浅(bug 需要多个调用方,而测试只有一个;单元测试重现不了触发 bug 的那条链),在那里写回归测试只会给假的安心。
**没有正确的接缝,这本身就是发现**:写下来(代码结构让这个 bug 没法被锁住),在 PR 里提出,交给评审。

有正确的接缝时:
1. 把缩小后的重现变成那个接缝上的失败测试,写上 `03-测试用例.md` 里对应的用例 ID(回归测试也要对应 03 的用例;没有对应的用例时,
   按开发 Agent 的规则在 Issue 上写 `[提问]` 请求扩大 03,重新做 D2)。
2. 看它失败。如果是靠改代码或测试数据强行造出的失败,和原样的副本比一下(`git diff`),确认改动真的生效了再相信它。
3. 修复。
4. 看它通过。
5. 用第 1 阶段的检查手段,对原来(没缩小的)场景再跑一次。

## 第 6 阶段:收尾

宣布完成之前:
- [ ] 原来的重现不再重现(再跑第 1 阶段的检查手段)
- [ ] 回归测试通过(或写明了没有正确的接缝)
- [ ] 所有 `[DEBUG-...]` 都删掉了(`grep` 前缀)
- [ ] 一次性的代码删掉了
- [ ] 最后证明正确的那个假设写进了提交说明或 PR,下一个排查的人能学到
